## 1. 背景：公式の情報の問題

高嶺のなでしこ（たかねこ）の出演・イベントの予定は、公式の 3 か所に分かれて発表されます。どれも単独では、予定の全体と最新の状態が分かりません。

| 発表される場所 | 主に載るもの | 問題 |
| --- | --- | --- |
| 公式サイトのカレンダー | ライブ・イベントの日時・会場・出演メンバー | 載るのが遅い。会場が「東京都内某所」のまま、詳細が「後日発表」のままなど、情報が古いことが多い。いつ変わったかが分からない |
| 公式サイトのお知らせ記事 | リリースイベントの詳細、申込・締切、ラジオ出演のまとめ | 新しい記事が積み重なり、探しにくい。1 つのイベントの情報が複数の記事に分かれ、申込・締切は本文に埋もれる。公開後に書き換えられても、どこが変わったか分からない |
| 公式 X（@takanenofficial） | 最初に出る情報。他団体のイベント、ラジオ・配信の出演、当日の案内、中止・欠席・変更、売り切れ・追加販売 | 投稿は流れていき、後から探しにくい。公式サイトに反映されないままのことが多い。告知の画像にしか書かれていない情報もある |

時刻・会場・受付の大きな変更は、公式 X とお知らせ記事に同時に出ることが多い一方、当日の変更、売り切れ、他団体のイベント、画像だけの情報は、公式 X にしか出ないことがよくあります。中止・欠席は、2025 年 12 月以降、公式 X にしか出ていません。
そのため、どれか 1 か所だけを見ていると、予定を見落としたり、中止になった予定に行ってしまったり、古い情報のまま申し込んだりします。

## 2. 目的

このツールは、公式の 3 か所の情報を自動で集めて、次の状態をつくります。

1. **1 か所で分かる:** 予定、申込・締切、当日に必要なことを、1 つの一覧と予定ごとのまとめで見られる。
2. **最新の状態が分かる:** どこで発表されたかに関係なく、後から出た情報を最新として反映する。
3. **根拠をたどれる:** どの情報も、元になった公式の発表を確かめられる。
4. **見逃さない:** 予定の追加・変更・中止と申込の締切を、知らせて気づけるようにする。
5. **当日に困らない:** 会場・当日の流れ・持ち物・出演時間など、行く前に必要なことが分かる。

これらを、自分のカレンダーアプリ、Web ページ、通知、一覧のファイルで使えるようにします。

## 3. 基本の考え方

| 考え方 | 内容 |
| --- | --- |
| 公式の情報に基づく | 予定の拠り所は公式の発表とする。公式でない情報は、公式にまだないものを補うためだけに使い、公式でないと分かるようにする |
| 後から出た情報を最新とする | どこで発表されたか（カレンダー・お知らせ・X）ではなく、いつ発表されたかで最新を決める |
| 根拠をたどれるようにする | 示す情報は、どの公式の発表に基づくかを確かめられるようにする |
| 確かでないことは、確かでないと示す | 推測で埋めない。読み取りや要約による情報、出演者が分からない予定などは、そうと分かるように示す。迷うときは、取り違えるより分けて示す |
| 公式の発信を尊重する | 公式の文章をそのまま載せない。最終的な確認は公式で行ってもらい、このツールは公式の情報への入り口になる |

してはいけないことの線引き（メンバーの今いる場所を広めないなど）は [機能仕様書](spec.md) の「2. 範囲」と「9.5 個人と権利への配慮」に、動かし続けるための条件（人の手をかけない、費用を抑える）は「9. 非機能要件」に書きます。

## 4. 解決できていることと、残っている課題

| 公式の問題 | このツールでの解決 | 残っている課題 |
| --- | --- | --- |
| カレンダーが遅い・古い | お知らせ記事・公式 X（告知の画像を含む）から先に取り込み、仮の会場や古いリンクを補う | 取り込みは決まった間隔で行うので、公式の発表から反映まで時間がかかる |
| お知らせが積み重なり、埋もれる | 予定ごとに記事をまとめて当日に必要なことを要約し、申込・締切を一覧とリマインドにする | 記事が書き換わったとき、何が変わったかを使う人に伝えていない |
| 公式 X の情報が公式サイトに反映されない | 公式 X だけの予定、画像だけの情報、出演時間、売り切れ、申込・締切を取り込み、後から出た方を採る | 当日の変更を届ける速さ。予定ごとのまとめに新しい情報が足されても気づきにくい。メンバー個人の X は読まない |

個々の作業は [バックログ](backlog.md) で管理します。
